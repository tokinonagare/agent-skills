# 验证他人交付的工作

## 核心

评审别人交付的改动时，有两件事**看报告永远看不出来**：

1. **报告里的数字不是证据** —— 它是一句转述。数字对不对、跑的是不是当前这版代码、有没有沿用 rebase 前的结果，都要你自己跑一遍才知道。
2. **测试存在 ≠ 测试能拦** —— 断言可能永远为真、可能因取值错误而恒红/恒绿、可能压根没覆盖到被改的那个元素。唯一的证明方式是**把修复改回去，看它是否真的变红**。

**核心原则：转述不是验证。绿色不是守卫。**

> **前置环节**：如果这份交付是你派出去的活，验收**之前**应先过独立 code review 并把结果回灌给作者
> （见 `reviewing-agent-deliverables`）。review 会推翻一部分改动，先验收等于白跑一遍数字。

## 何时使用

- 接手/评审另一个 agent 或同事「已完成」的分支
- 对方报告里出现 `N files / M tests passed`、`VR 15/15`、`0 error`、`已实机验证` 这类数字或结论
- 你准备把这些结论**继续往上转述**（写进 MR 描述、issue 评论、给用户的汇报）

**不适用**：你自己刚写的代码（那是 TDD 的范围）；纯文档/文案改动且无测试声明。

## 纪律一：数字自己跑，不转述

对方报的每一个数字，**在你自己的环境里重跑一遍**再引用。至少覆盖：单测、类型检查、lint、以及被改动区域相关的视觉/端到端测试。

三个常见的「数字是真的、但结论是假的」情形：

| 情形 | 为什么数字对而结论错 |
|---|---|
| 分支基点过时 | 数字是在旧 dev 上跑的；rebase 后未必成立 |
| 命令口径不对 | 例：提交之后再跑「只看未暂存改动」的 lint 脚本，会输出 `No changed files to lint.` 并 exit 0 —— 一个什么都没检的绿灯 |
| 覆盖面不含被改处 | 视觉基线全绿，是因为那些截图**压根没拍到**被改的组件（未展开的抽屉、未激活的面板、portal 浮层） |

第三种最隐蔽：**先确认那些用例真的会渲染到你改的东西**，再决定「全绿」意味着什么。

## 纪律二：守卫用变异证明

```
把修复点临时改回缺陷态 → 相关断言必须变红 → 还原 → 确认 git diff 为空
```

变红了，这条测试才算守卫；仍然绿，这条测试是装饰。**别只删一种**：把修复删掉是一种变异，把它替换成另一种"看起来也对"的写法是另一种——后者才是漏网的那类。

只错一帧、只错一种角色、只在某个视口才错的缺陷，普通断言极容易压根测不到；这类改动**必须**做变异。

变异完**必须还原**并核对工作区干净——变异注入留在树上，是比原缺陷更坏的结果。

### 文本断言（读源码正则匹配）的五种必做变异

一批 5 单里 **4 单栽在同一类**：新写的守卫「改值会红、搬进注释也会红」，看起来是真守卫，
唯独放行「换个属性名前缀」「挪进嵌套块」「同选择器再写一遍」——而这几种恰好是重构与手滑
最常见的退化形态。缺任何一种就不算证明过：

| # | 变异 | 实测过的漏网例 |
|---|---|---|
| 1 | **改值** | 最基本，一般都会红 |
| 2 | **把声明搬进注释** | 注释里的等价字面串骗过裸读的断言 → 修法：断言前先剥注释 |
| 3 | **换属性名前缀** | `/color:\s*#3f6580/` 被 `background-color:` 命中 → **17 passed 全绿**；`/gap:\s*12px/` 被 `column-gap:` 命中（flex-column 下间距归零）→ **17 passed 全绿**。修法：锚定 `/(^\|[^a-z-])color:\s*#xxx/` |
| 4 | **把声明挪进嵌套块** | 整块 `toMatch(/padding:\s*16px\s+20px;/)` 下，声明从 wrapper 顶层挪进 `textarea{}` → **7 passed 全绿**，而实际渲染 wrapper 已失去 padding。修法：只取块的直接声明（`own()` 语义） |
| 5 | **同选择器再写一遍（重复声明覆盖）** | 在文件末尾另起一条 `.x { ... }`，同选择器同优先级、**后声明覆盖前声明**，浏览器里缺陷真的会长回来 → **7 passed 全绿**。根因是取块的 helper 用 `source.search()` **只定位第一个匹配块**，对后续重复声明视而不见。修法：聚合文件中**所有**匹配该选择器的块，或在文件层面断言该选择器只应出现一次 |

第 5 种最容易被漏，因为它不需要任何"聪明"的写法——**就是把规则再写一遍**。
守卫作者通常把「等价回退」的想象力限定在自己修的那种形态上（比如"还得挂 `.interview-card` 前缀"），
于是只堵了那一种。

阴险之处：**同一份守卫里有的条目安全、有的假绿**——`background:` 那种不受影响
（`background-color: x` 不含子串 `background: x`），所以「我做过变异、红了」这个结论本身会漏。

**更便宜的做法是把这五种写进派活 prompt**，而不是事后 review 抓。事后抓意味着返工一轮。

### 变异必须对应**真实的回退路径**

变异不红有两种可能，别混为一谈：**守卫弱**，还是**你这个变异根本不构成缺陷**。

实测教训：验一条「`.interview-card` 不再承载未开始态子规则」的守卫时，我注入了
`.interview-card .interview-not-started { background: ...; border-radius: 20px }`，守卫没红，
我一度判「没修好」。查下去才发现——组件渲染的 `.interview-not-started` 外层是 `.interview-layout`
而**不是** `.interview-card`，那条规则在真实 DOM 里不匹配任何元素，**是无害变异，不红才是对的**。
换成真实回退形态（`.interview-card .interview-not-started-title` 独立嵌套块）重跑，正常变红。

**下结论前先问：我注入的这个东西，真的会让用户看到缺陷吗？** 答不上来就先去看组件实际渲染的
类名 / DOM 结构，别急着判作者没修好。冤枉一次的成本是一轮无谓返工加一次信任损耗。

### 重构类交付：做测试数量对照

「重构把守卫弄没」不会表现为红，而是表现为**测试悄悄变少**。抽公共 mixin / 提取函数 / 合并
断言这类改动，必须在**改动前后各跑一次同范围**，把数字摆在一起：

```bash
# 在 dev 上跑一次，在分支上跑一次，同一路径范围
npx vitest run <被影响的目录> 2>&1 | grep -E "^ *(Test Files|Tests) "
```

实测一次：`Candidates 580 → 575`（-5）、`common/styles 260 → 268`（+8），净 +3。
逐条追下去确认少掉的 5 条是两份文件里的**重复**断言、新增 8 条覆盖了 mixin 定义处——
是去重不是丢失。**但如果只看到「575 全绿」，你不会知道曾经有 580。**

### 变异前先确认变异**真的生效了**

最常见的假验证不是「守卫太弱」，而是**你根本没改到东西**：替换脚本的正则没匹配上、
缩进猜错了、或者那个字符串在文件里出现了**两次而你改的是另一处**。
此时测试当然全绿，而你会把这个绿当成「守卫覆盖不到」——结论正好反了。

**落地做法**：每次变异后、跑测试前，插一步硬证据：

```bash
git diff -- <file> | grep -E '^[+-][^+-]'     # 必须看到预期的那几行
# 或：打印被改对象的实际取值 / grep -c 关键字，与预期数字对上
```

对不上就**别跑测试**——那次结果不作数，先修变异脚本。

三个反复踩到的具体形态：

| 形态 | 症状 | 办法 |
|---|---|---|
| 同名字符串出现多次 | 改到了另一个规则块，目标块纹丝不动 | 先按块边界定位（找到目标选择器 → 取到它的 `}`），只在块内替换 |
| 缩进/空白猜错 | 替换静默不发生 | 用不含前导空格的正则，或先 `grep -n` 打出真实文本 |
| shell 变量被当成单个参数 | 测试命令跑了个空集，输出「全过」 | zsh 不做词分割；用显式路径或数组，别指望 `$FILES` 展开 |

> 判据很简单：**没看到 diff，就没有变异**。绿是无意义的绿。

## 常见借口对照表

| 借口 | 事实 |
|---|---|
| 「我这边不需要再跑一遍全量」 | 那你引用的就是别人的结论。要么跑，要么在报告里标明「未跑、采信作者」 |
| 「作者已经跑过了」 | 作者跑的是 rebase 前 / 不同命令口径 / 不含你关心的那块 |
| 「测试文件在那儿，覆盖了」 | 断言可能恒真。没变异过就没有证据 |
| 「基线全绿说明没回归」 | 也可能说明基线拍不到这块。先查覆盖面 |
| 「变异测试太麻烦」 | 改一个值 + 跑一条 spec + 还原。比放过一个假绿便宜得多 |
| 「我读了 diff，逻辑是对的」 | 读 diff 查不出「测试能不能拦」 |

## 危险信号

- 你的评审结论里出现了作者报告里的数字，而你没跑过
- 你写下「测试是真守卫」但没做过变异
- 你把「全绿」当成「无回归」，却没确认覆盖面
- 你标了「已核实」，实际做的是「读过」
- 变异注入还留在工作区
- 你做了变异但**没确认它生效**，就把「仍然全绿」当成结论
- 变异没红，你直接判「守卫弱 / 作者没修好」——先确认**这个变异真的构成缺陷**，无害变异不红是对的
- 文本断言只做了「改值」和「搬进注释」两种，没做**换属性名前缀**、**挪进嵌套块**、**同选择器再写一遍**
- 重构类交付你只看到「全绿」，没有和改动前做**同范围的测试数量对照**

**以上任一条成立：先跑，再下结论。**

## 例子：一次真实的假绿

某处样式修复配了 4 条断言，断言方式是对 `.less` **源码文本**做正则匹配。

作者与第一位评审都做过「删掉修复 → 变红」，判定为真守卫。但正则匹配的是源码文本、**不区分注释与规则**，而同文件的注释里恰好有一段完整写出该规则的交叉引用。

第二种变异（**删掉真规则、把那段注释搬进作用域块内**）下：

| 变异方式 | 旧断言 |
|---|---|
| 删掉真规则（注释留在块外） | 红 ✅ |
| 删掉真规则 + 注释搬进块内 | **4 条全绿** ❌ |

修法是断言前先剥注释。**只做一种变异会漏掉这类洞。**

同一份改动上还出现过反向问题：断言 helper 取块内容时差了一位（循环从 `{` 起、深度直接为 1），5 条断言全部因为「取不到内容」而失败——那是**假红**，同样只能靠变异分辨。
