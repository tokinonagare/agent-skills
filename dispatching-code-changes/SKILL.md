# 代码改动一律派给独立 agent

## 铁律

**涉及代码改动的请求，默认不是「你去改」，而是「你去派」。**

除非用户明说「你直接改」，否则一律：

```
新建 worktree（基点显式指定，别用当前 HEAD）
  → 新建 tab
  → 在 tab 里起 agent（类型默认与当前 agent 一致，用户可指定）
  → 把活派给它
  → 交付回来先过独立 code review，结果回灌给作者改
  → 你负责调研、review 指派、验收、合并、清理
```

**交付回来的下一步是 review，不是验收**——机制见 `reviewing-agent-deliverables` skill。

**不在主仓工作区直接 Edit/Write 业务代码。**

## 何时适用

**适用**：修 bug、加功能、重构、改样式、改配置、改测试——任何会落进 git 的代码改动。

**不适用**（这些你自己做）：
- 只读调研：查根因、读代码、跑测试量数据、看 VR 基线
- 回答问题、解释机制、写分析
- 派活所需的准备：建 worktree、写 issue、写 prompt
- 指派与裁定 code review（见 `reviewing-agent-deliverables`）
- 验收：重跑数字、做变异证明、真机复现
- 用户明说「你直接改」「不用派 agent」

判据很简单：**这次操作会不会产生一个需要评审和合并的 diff**。会，就派。

## 为什么

每个改动有自己的分支 / worktree / MR / issue：可并行、可追溯、可回滚，互不干扰，主仓保持干净。
你直接动手会绕过这套——改动散落、没有评审痕迹、多个改动挤在一个工作区互相污染。

**这不是流程洁癖。** 实测过：主仓被某个会话 checkout 到别的分支后，后续所有「以为在 dev 上」的判断全部失真。

## 合理化对照表

从基线测试里抓到的借口，逐条封死：

| 借口 | 事实 |
|---|---|
| 「就改一行，开 worktree 太重」 | 行数不是判据，**会不会产生 diff** 才是。预置有固定脚本，一分钟的事 |
| 「用户让我修，没说要派 agent」 | 默认就是派。用户要你直接改会明说 |
| 「先改了再说，反正能回滚」 | 回滚的成本不在 git，在你已经污染了主仓工作区 |
| 「我已经调研完了，顺手就改了」 | 调研完正是该派活的时刻——把调研结论写进 issue，让 agent 照着做 |
| 「只是改个注释 / 文案 / 测试」 | 一样进 git、一样要评审。照派 |
| 「派 agent 还要写 prompt，我自己改更快」 | 快的是这一次，慢的是后面所有人查这个改动从哪来 |
| 「worktree 环境预置太麻烦」 | 那是脚本该解决的问题，不是绕过规矩的理由 |

## 红旗——出现即停

- 你正准备对业务代码调 `Edit` / `Write`，而这次会话没派过 agent
- 你想「这个太小了不值得派」
- 你已经在主仓改了文件，打算「改完再说要不要建分支」
- 你说服自己「用户的语气是让我直接改」，但用户并没有明说

**任一条成立：停手，去建 worktree。**

## 怎么派

具体机制（worktree 预置清单、起 agent、盯进度、边界核验、过硬闸清理）见
**`herdr-orchestration`** skill；交付回来的 review 环节见 **`reviewing-agent-deliverables`** skill。仓库特有的事实（基点分支、端口分段、验证口径）
见该仓的并行开发文档（本仓是 `docs/agents/parallel-worktree-dev.md`）。

**agent 类型**：默认与当前 agent 一致（当前是 claude 就派 claude）；用户指定了就用指定的。

**派的时候点名档位**。派不派是二元的，**派多重不是**——不给验证预算，agent 会跑满：
实测一个只改几行 SVG 的单跑了两次全量单测、一个 mock 顺序单跑了 35 次 VR。
档位判据见 `reviewing-agent-deliverables` §一，每档的验证预算见
`herdr-orchestration` §四「验证预算」。**判档看触点，不看行数**——
「只改了几行」这个直觉实测经常是错的。
