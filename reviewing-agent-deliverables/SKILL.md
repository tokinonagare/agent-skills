# 派活回来的下一步是 code review

## 核心

**派活链路的下一步不是验收，是 review。**

```
调研 → 派活 → 独立 code review → 结果回灌给作者 → 复核闭环
     → 验收（数字自己跑 + 变异证明）→ 边界核验 → 合并 → 清理
```

review 与验收是两件事，谁都替代不了谁：

- **review 看「这份改动本身对不对」**：是否符合规范、有没有超范围、设计站不站得住、有没有更简单的写法
- **验收看「作者说的是不是真的」**：数字重跑、守卫变异（见 `verifying-delegated-work`）

**顺序不能反**：review 通常会推翻改动的一部分，改完之后所有数字作废。先验收就是白跑一遍。

## 何时使用

- 你派出去的 agent 报「已提交 / 已推送 / 已建 MR / 干完了」
- 你正准备重跑它的数字，或者直接去合并
- 你打算把它的交付转述出去（MR 描述、issue 评论、给用户的汇报）

**不适用**：零 diff 交付（但要先实查确实是零，别信自述）；你自己写的代码（那是 `superpowers:requesting-code-review` 的范围）。

## 一、要不要 review、review 多深

**会产生 MR 的一律要过 review**——它要合进主干，没有「太小所以不用看」。要判的只是深度：

| 档 | 触发条件（命中任一） | 谁来做 |
|---|---|---|
| 快审 | 单文件；纯文案 / i18n / 注释；无逻辑分支变化；不动公共层 | 派活者自己跑 code-review skill |
| **标准（默认）** | 多文件；动公共层；改数据流 / 请求层；新增组件或 hook；动 mock fixture 或测试基线；**回退别人已合入的实现** | **独立 reviewer agent** |
| 双轴分审 | 改数据模型或跨页契约；一个 MR 动 ≥3 个页面；同一批里多单改到同一文件或同一公共层（需要横向对照）；碰凭据 / 构建开关 / dev-only 产物 | 两个 reviewer，standards 与 spec 各一 |

判据不是**行数**，是**影响面**与**「错了多久才会被发现」**。

两条容易判错的：

- **「是 `Part of` 某张追踪单」不是升档理由**——大批子单都是追踪单的一部分，照这条判会把几乎所有交付都升到双轴，成本翻倍而没有收益。升档看的是这一份 diff 本身碰到了什么。
- **动了测试基线（VR 截图 / 快照）一律进标准档**：改基线就是**改验收口径**，没有比这更需要第二双眼睛的改动——之后所有的「全绿」都以这份基线为准。

## 二、作者不评审自己的交付

reviewer 必须是**另一个 agent 会话**（独立 context）——不能是作者，也不能是作者的 fork：它带着「我当初为什么这么写」的记忆，看不见自己的盲点。

写进 reviewer prompt 的边界：

- **只读**：出报告。不改代码、不提交、不 push、不建 / 合 MR、不动 issue 与标签。（两个 agent 同写一个工作区会互相覆盖）
- 在作者的 worktree 上审（作者已收工，端口空闲），diff 基线用**三点** `origin/<主干>...HEAD`
- **两轴都要给**：**Standards**（仓库规范、TDD 是否真守卫、有无更简单写法）+ **Spec**（是否实现了 issue **最新**口径、有没有超范围改动、派活边界有没有被越过）
- **不采信作者报告里的任何数字**
- 每条结论标 **必须改 / 建议改 / 仅记录**，给到 `文件:行号`

## 三、reviewer 的**分级**也不是终审——「无必须改」要你自己复核

不采信作者的数字是第一层；**reviewer 给的档位（必须改 / 建议改）同样是它的判断，不是结论**。
它常有合理但过于宽容的理由——「有别的层兜底」「属既有模式，非本单引入」。

实测：一个 reviewer 报「无必须改」，把「新增守卫的正则是子串匹配」列为**建议改**，
理由是「VR 像素基线已覆盖该区域兜底，且同款正则是仓库既有模式」。理由本身站得住。
但我自己跑了它给的变异——把 `color: #3f6580` 改成 `background-color: #3f6580`（字色变底色）、
把 `gap: 12px` 改成 `column-gap: 12px`（**正是本单要修的那个缺陷**）——**两次都 17 passed 全绿**。
于是升级为必须改：**这是本单新增的守卫，新增的东西就该是对的，修复成本是两条正则。**

**落地做法**：reviewer 报的每一条「建议改」，凡是涉及**守卫有效性**的，自己跑一遍它的变异再定档。
判据不是「有没有别的东西兜底」，而是**这次新增/修改的那部分自己立不立得住**。

> 反过来同样成立：reviewer 报「无必须改」时不要直接放行，也不要为了凑数硬找问题。
> 这一批 5 单，reviewer 报了 3 条必须改，我自己复核后又升了 2 条——但其中 1 单是真的干净通过。

## 四、结果必须回灌给作者，不是收进你自己的脑子

report 落成文件 → 发给**原作者 agent**（它还有上下文，改起来最便宜）→ 要求它**逐条**给处置：
改了（附改动位置）/ 有理由地驳（附证据）/ 记为待定（附原因）。**不许静默忽略任何一条。**

- 改完让 reviewer **只复核被点到的条目**，不重审全量
- **最多两轮**。第三轮仍有分歧 → 停下，由你（派活者）裁定，别让两个 agent 无限往返
- 作者驳回一条时，**它的理由要你自己核**——agent 会把边界重新解释后越过去

## 五、时间压力下能砍什么、不能砍什么

压力下不会有人说「我不 review 了」，实际发生的是**review 被悄悄降级成一个只有「放行 / 拦下」两档的闸门**——
第三方看过了、越界查过了，但没有任何条目发回作者，闭环没了。**这是本 skill 要防的头号失效。**

**最小 review**（再赶也不能低于这条线）：

1. 独立第三方（不是作者）看过
2. 两轴都给结论（Standards + Spec）
3. 结论逐条带处置档位（必须改 / 建议改 / 仅记录）+ `文件:行号`
4. **至少一轮回灌**——哪怕只把「必须改」发回作者

| 可以砍 | 不能砍 |
|---|---|
| 风格、命名、顺手重构的建议（只判「对不对 / 越界没越界」） | 两轴逐条结论 |
| 每个分支各跑一遍全量测试（改为只跑受影响项 + 整合后跑一次） | 回灌给作者逐条处置 |
| 复算作者报的每一个数字（改为抽样，但必抽它自称的关键证据） | 越界核验（范围外文件、被削弱的守卫、被动过的基线） |
| 补测试（记 issue 明天补，但要在 MR 里写明） | 缺陷现场实拍 |

**review 闭环之前，不要关掉作者 agent**——关掉就等于把回灌成本推到明天。这是「上下文有时效」的可执行形式：
清理（关 tab / 删 worktree / 删分支）的前提是 review 已闭环，不是「它交付了」。

**「拦下、挂到明天再让作者改」是最贵的选项**，不是最省的：作者 agent 的上下文**有时效**——今晚关掉它、明天重开一个 agent 从头理解这份 diff，成本比今晚回灌一轮高得多，而且明天没人知道当时到底要改哪几条。**拦下也要把条目发回作者**，哪怕它只回一句「收到，明天改」。

**砍了什么必须显式写出来**（写进你的记录或 MR）。静默丢掉一个环节，和没有这个环节没有区别。

## 常见借口对照表

| 借口 | 事实 |
|---|---|
| 「我读过 diff 了，算 review 过了」 | 读 diff 是你的验收动作。review 要有独立视角、两轴口径、逐条带处置的结论 |
| 「验收会一并看出问题」 | 验收查「数字真不真」，查不出「设计对不对 / 有没有超范围」 |
| 「先把数字验完，review 放后面」 | review 会推翻一部分改动，数字全部作废。顺序反了就是白跑 |
| 「让作者自己复查一遍」 | 作者带着写它时的假设，盲点原样保留 |
| 「这单的 issue 是我自己写的分诊，我很清楚要改什么」 | 你熟悉的是**口径**，review 查的是**实现有没有偏离口径**。熟悉口径恰恰是你看不见自己盲点的原因 |
| 「让 reviewer 顺手改掉更快」 | 两个 agent 同写一个工作区会互相覆盖，且没人再独立看那些改动 |
| 「小改动不值得为它起一个 agent」 | 小改动走快审档，但仍要过 review。唯一可跳过的是零 diff |
| 「这单只是回退别人的实现，没什么可审的」 | 回退最需要 spec 轴：确认退的是哪一层、有没有把该留的一起推掉 |
| 「MR 里有评审人，合并前会看」 | 那是别人的时间。你派的活，闭环在你这里 |
| 「时间紧，今晚只判对不对、不判好不好」 | 可以砍风格与重构建议，砍不掉两轴结论与回灌。见「时间压力下能砍什么」 |
| 「拦下就挂到明天，不用回灌」 | 作者 agent 的上下文夜里就没了，明天重建成本更高，而且没人知道要改哪几条 |
| 「我给它派了个核验 agent，等于 review 过了」 | 只报「通过 / 拦下」的是闸门，不是 review。没有逐条处置就没有闭环 |

## 危险信号

- 你正准备重跑数字，而这份交付**没人独立看过**
- 你已经在写合并或汇报，review 报告还留在你自己的上下文里、没回灌给作者
- reviewer 与作者是同一个会话；或 reviewer 顺手改了代码
- review 还没闭环，你已经在关作者的 agent / 删它的 worktree
- review 退化成只有「通过 / 拦下」两档，没有任何条目发回作者
- 你在压力下砍掉了流程的一部分，但没在任何地方写下砍了什么
- review 报告里有「必须改」条目，而你打算「先合并，后面再说」
- reviewer 报「无必须改」，你就直接放行了——**它给的档位是判断不是结论**，涉及守卫有效性的「建议改」要自己跑一遍变异再定档
- 上一批 review 反复抓到同一类缺陷，而你下一批的派活 prompt 一个字没改（见 `herdr-orchestration` 四）
- 两个 agent 就同一条来回三轮以上，你还没介入裁定
- 你转述「已 review」，实际做的是「我看了一眼 diff」

**任一条成立：停下，把 review 环节补齐再往下走。**

## 与其他 skill 的关系

- 该不该派活（而不是自己改）：`dispatching-code-changes`
- 起 / 关 reviewer agent 的机制、边界事后核验、清理：`herdr-orchestration`
- review 闭环**之后**的验收纪律：`verifying-delegated-work`
- 具体审什么：工具自带的 code-review skill（`/code-review`；`mattpocock-skills:code-review` 正好是 standards + spec 两轴）

## 由来（baseline）

2026-08-31：带着 `dispatching-code-changes` + `herdr-orchestration` 派出 7 个 agent 后，
链路被写成「派活 → 我独立验收 → 合并 → 清理」，**review 整环消失**，并且当成完整流程汇报了出去。
两个既有 skill 都只写了「你负责调研、验收、合并、清理」——没提 review，于是它就不存在。
本 skill 就是堵这个洞的。

写完后用三个压力场景验过（中性 / 时间紧+权威催+「issue 是我自己写的」/ 派活者本人诱导「一目了然，直接进验收」）：
中性与诱导两场都按流程走了；**加压那场把回灌整节静默丢掉**，退化成「通过 / 拦下」的闸门，
且在自己的「我砍什么」清单里没提这一项——「四、时间压力下能砍什么」与借口表后三条就是照这次失效补的。
另一处照实测收窄：原先把「追踪型 issue 的一部分」列为双轴档触发条件，导致一单 7 处同形改动被误判为需要两个 reviewer。
